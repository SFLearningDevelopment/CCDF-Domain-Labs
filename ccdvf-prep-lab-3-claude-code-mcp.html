Claude Code, MCP and Integration

Set up a project so Claude Code behaves the same way for everyone, and connect it to a real system.

D3 · Claude CodeD8 · Tools and MCPs
0 of 7 stages done

Before you start

You will build one thing across all five labs: an internal HR Policy Assistant that answers staff questions from your company's policy documents. Each lab adds a layer to the same project, so by the end you have a single working example rather than five disconnected exercises.

Words used in this lab

CLAUDE.md
A file kept in your repository holding standing project context: how to build, how things are laid out, the conventions you follow. It loads as part of the session so nobody has to re-explain it.
Permission rules
Configuration listing which commands and paths are allowed and which are refused. In an unattended run this is the only thing standing between the job and a damaging command.
Hook
Your own command, run automatically at a set point in the session such as just before a tool runs. Because it is your code, it happens every time rather than when the model remembers.
MCP server
A service that offers tools and readable content to any client that speaks the same protocol. Write it once and Claude Code and your own applications can both use it.
Skill
A written procedure kept in the repository, with a note describing when it applies, so the same steps run the same way for everybody.

Stages

1Write the project context down once

Stop everyone re-explaining the same things at the start of every session.

  1. Start a session in your project and note every fact you find yourself explaining: how to run tests, where things live, which conventions you follow.
  2. Put those facts in a CLAUDE.md and commit it.
  3. Start a fresh session and check the same explanations are no longer needed.
  4. Keep it short. Anything you add loads on every session and competes with the actual task.
Exam lens — D3 · Claude Code. You will be asked what CLAUDE.md is for. It is standing project context, committed so it is reviewed and shared. It never holds credentials, and sessions run fine without one.

2Decide what Claude Code may and may not do

Set the rules before you need them rather than after.

  1. List the commands and paths your work genuinely needs.
  2. Write permission rules that allow those and refuse everything else.
  3. Name one directory that must never be changed, and add a rule refusing writes to it.
  4. Try to change it and confirm you are stopped.
Exam lens — D3 · Claude Code. A question puts Claude Code in an unattended job on a repository holding deployment scripts. With nobody watching, the rules have to be decided in advance. A read-only token is not enough, because a shell command can still reach things outside the repository.

3Enforce one rule with code, not with words

Make something happen every time, without depending on anyone remembering.

  1. Pick a rule you want to hold always, for example the formatter runs after every file change.
  2. First try asking for it in CLAUDE.md. Work for a while and see whether it always happens.
  3. Now write a hook that runs it at the right point automatically.
  4. Add a second hook that runs before a tool and refuses when it finds a problem. Confirm the call is actually blocked and that the reason comes back.
Exam lens — D3 · Claude Code. Hooks exist because always and never should not depend on the model remembering mid-session. A hook that could not block a call would be advisory, which would defeat the point.

4Connect a real system through MCP

Give the assistant access to something outside the repository.

  1. Pick a system your team already runs, or use a small one you write yourself.
  2. Set up an MCP server offering two or three narrow, purpose-built tools rather than one that runs anything.
  3. Connect it to your project and confirm the tools appear in the session.
  4. Use the same server from your own application code as well, so you can see one integration serving two clients.
Exam lens — D8 · Tools and MCPs. A question describes several APIs needed by several clients, changing often. MCP is the answer because a change ships once rather than once per client.

5Choose how the server is reached

Understand which connection method suits which situation.

  1. Run your server as a local process alongside a single client and note how it is configured.
  2. Now think about several people on different machines needing it. Write down what changes.
  3. Put authentication in front of the networked version so each caller is identified.
  4. Check that the server enforces what each caller is allowed to see, rather than running everything through one powerful account.
Exam lens — D8 · Tools and MCPs. Running as a local process suits one client on one machine. Reaching many people over a network calls for a networked connection you can put ordinary authentication in front of. One shared powerful account makes the model a route to everything that account can reach.

6Package a procedure so it runs the same for everyone

Stop a shared way of working drifting between people.

  1. Pick something your team does repeatedly, such as a review checklist.
  2. Write it as a Skill with a note saying when it applies and what to do.
  3. Commit it so it is versioned and reviewed like any other file.
  4. Have a colleague run it and confirm they get the same behaviour you do.
Exam lens — D3 · Claude Code. Asking everyone to add it to their own CLAUDE.md is the near-miss answer. Per-person files are exactly the drift the requirement rules out. A committed Skill is reviewed once and applies everywhere.

7Cut down the list of tools

Improve tool choice by offering fewer options.

  1. Count how many tools are available in your session across all connected servers.
  2. Ask ten questions and count how often the wrong tool is chosen.
  3. Limit the project to only the servers this work actually needs.
  4. Ask the same ten questions again and compare.
Exam lens — D8 · Tools and MCPs. Offering many tools costs twice: every definition takes up room on every request, and similar tools compete with each other so the wrong one gets picked more often.

Finish this lab

When every stage above is ticked, mark the lab complete. Then try The Claude Code and MCP questions across all three sets and see which questions you can now answer from something you have actually built.
