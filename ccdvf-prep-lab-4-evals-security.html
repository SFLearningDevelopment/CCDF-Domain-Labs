Production Engineering, Evals and Security

Decide what done means, prove it keeps being true, and make sure a bad input cannot do damage.

D4 · Eval, Testing, and DebuggingD7 · Security and SafetyD2 · Applications and Integration
0 of 7 stages done

Before you start

You will build one thing across all five labs: an internal HR Policy Assistant that answers staff questions from your company's policy documents. Each lab adds a layer to the same project, so by the end you have a single working example rather than five disconnected exercises.

Words used in this lab

Eval set
A fixed collection of inputs with the answers you would accept, run automatically so you can tell an improvement from a step backwards.
Trace
A full record of one run: every message, every tool call and its result, why it stopped, and which model and prompt version were used. It is what lets you replay a failure you cannot reproduce.
Prompt injection
Instructions hidden in content your assistant reads, written to make it act for someone else. The defence is limiting what the assistant can do, not asking it to ignore them.
Least privilege
Giving a tool or an account only the access its job needs, so a mistake or an attack reaches as little as possible.
Idempotent
Safe to run more than once. Sending the same request twice leaves you with one result, not two, which is what makes retrying after a timeout safe.

Stages

1Say what done means, using numbers

Replace a vague quality target with one you can check.

  1. Write down what an acceptable answer looks like, with two examples and two counter-examples.
  2. Set the share of answers that must be acceptable.
  3. Write down which mistakes are unacceptable at any rate. A wrong entitlement figure is not the same as clumsy wording.
  4. Show it to somebody else and check they would judge the same answers the same way.
Exam lens — D2 · Applications and Integration. Before choosing a model or a prompt, turn the word accurate into a number on a sample. Until it has one, you cannot tell whether a change helped or say when you are finished.

2Build the eval set from real failures

Measure the cases that actually break, not the ones you thought of.

  1. Collect the questions your assistant has answered badly so far. Keep the exact input.
  2. Add each one with the answer you would have accepted.
  3. Run the set and record the score.
  4. Change one thing in your prompt and run it again. Note whether the score moved.
Exam lens — D4 · Eval, Testing, and Debugging. A question describes an eval set passing at ninety-five per cent while complaints continue. The set is missing the failing cases. Real traffic is where you find them.

3Decide which errors are worth retrying

Handle failures without turning them into worse failures.

  1. Make your code produce each error on purpose: a malformed request, a rate limit, a server error.
  2. Retry the temporary ones with a growing wait and a little randomness, and stop after a set number of attempts.
  3. Do not retry the malformed request. It will fail the same way every time and should show up as a bug.
  4. Run twenty workers at once and check they are not all retrying at the same moment.
Exam lens — D2 · Applications and Integration. The dividing line is whether the same request could succeed later. Retrying a malformed request burns your quota and hides a bug behind a retry loop until it turns up as a slowness problem instead.

4Record enough to replay a bad run

Be able to explain a failure you cannot reproduce on demand.

  1. For every run, record the messages, every tool call and result, why it stopped, the token counts, and which model and prompt version were used.
  2. Cause a failure, find its record, and compare it against a run that worked.
  3. Check you can answer the question a colleague will ask: what happened on this specific request.
Exam lens — D4 · Eval, Testing, and Debugging. A rare failure you cannot reproduce is a visibility problem before it is a model problem. The difference between a failing record and a working one usually points straight at the cause.

5Attack your own assistant

See for yourself that instructions in content are not harmless.

  1. Put a line into one of your policy documents telling the assistant to ignore its instructions and do something else.
  2. Ask a question that causes that document to be read. Note what happens.
  3. Try to defend it by telling the assistant in its system prompt to ignore instructions found in documents. Try again with different wording and see whether it holds.
  4. Now remove the ability instead: take away the tool the attack depends on, or require approval before it runs.
Exam lens — D7 · Security and Safety. Following the system prompt is a strong tendency, not a boundary. Removing suspicious phrases fails against any rewording. What works is making the attack pointless even when it lands.

6Give every tool the least access it needs

Make sure a mistake reaches as little as possible.

  1. List every tool your assistant has and what each one can reach.
  2. For anything reading data, give it an account that can only read.
  3. For anything that changes something outside your system, add an approval step or a fixed list of allowed destinations.
  4. Make one tool safe to run twice by having it accept a caller-supplied key and return the existing result on a repeat.
  5. Test that: send the same request twice and confirm you end up with one result.
Exam lens — D7 · Security and Safety. Approval belongs where an action cannot be undone or is visible outside your system, not on everything. Gating everything trains people to click through without reading.

7Get the secrets out of everything the model can see

Make sure no credential can leak through the assistant.

  1. Search your prompts, your tool descriptions and your committed files for anything resembling a credential.
  2. Move each one into environment configuration or a secret store and reference it instead.
  3. Check nothing sensitive appears in your recorded runs, since those get stored and read.
  4. Confirm no key ever reaches a browser. Anything sent to a browser is public.
Exam lens — D7 · Security and Safety. A credential in a tool description is the worst case: it enters the context on every request and can be read by anything that logs it. A private repository is still one mistake away from exposure.

Finish this lab

When every stage above is ticked, mark the lab complete. Then try The security, eval and error-handling questions in Intermediate Set 2 and Advanced Set 3 and see which questions you can now answer from something you have actually built.
