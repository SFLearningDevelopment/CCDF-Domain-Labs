The project

You build one thing across all five labs: policy-assistant, an internal tool that answers staff questions from your company's HR policy documents. Every stage changes the same project, and you are shown exactly what changed. Pick Python or TypeScript once and the whole track follows it.

Words used in this lab

Eval set
A fixed collection of inputs with the answers you accept, run automatically so you can tell an improvement from a step backwards.
Trace
A full record of one run: every message, tool call and result, why it stopped, and which model and prompt version were used. It is what lets you replay a failure you cannot reproduce.
Prompt injection
Instructions hidden inside content your assistant reads, written to make it act for somebody else. The defence is limiting what it can do, not asking it to ignore them.
Least privilege
Giving a tool or account only the access its job needs, so a mistake or an attack reaches as little as possible.
Idempotent
Safe to run more than once. The same request twice leaves one result rather than two, which is what makes retrying after a timeout safe.

Stages

1Say what done means, using numbers

Replace a vague quality target with one you can check.

  1. Write the criteria file. Two examples and two counter-examples, so somebody else can apply it the same way.
  2. Set the share of answers that must pass.
  3. Separate the mistakes that are unacceptable at any rate. A wrong entitlement figure is not the same as clumsy wording.
  4. Show it to a colleague and check they would judge the same answers the same way.

2Build the eval set from real failures

Measure the cases that actually break, not the ones you imagined.

  1. Create the eval cases file. Seed it with every question your assistant has answered badly so far.
  2. Include the two categories separately: normal questions, and the ones that must never be answered wrongly.
  3. Write the runner and run it.
  4. Change one thing in your prompt and run it again. Note whether the score moved.

3Decide which errors are worth retrying

Handle failure without turning it into worse failure.

  1. Add the retry wrapper and route every API call through it.
  2. Note which errors are retried and which are not: a malformed request will fail identically forever.
  3. The jitter matters. Without it, twenty workers retry in lockstep and rebuild the spike.
  4. Test it by setting an invalid model name and confirming it fails immediately rather than after five attempts.

4Record enough to replay a bad run

Be able to explain a failure you cannot reproduce on demand.

  1. Add the trace writer and call it from the agent loop.
  2. Record the full message list, every tool call and result, stop reasons, token counts, and the model and prompt versions.
  3. Cause a failure, find its trace, and compare it against a trace that worked.
  4. Confirm you can answer: what happened on this specific request.

6Give every tool the least access it needs

Make sure a mistake or an attack reaches as little as possible.

  1. Add the tool registry: each tool declares what it reaches and whether it needs approval.
  2. Anything read-only gets a read-only account.
  3. Anything with an effect outside your system needs approval or a fixed destination list.
  4. Make one tool safe to run twice using a caller-supplied key. Send the same request twice and confirm you get one result.
