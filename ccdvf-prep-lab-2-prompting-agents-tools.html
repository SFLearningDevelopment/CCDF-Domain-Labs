The project

You build one thing across all five labs: policy-assistant, an internal tool that answers staff questions from your company's HR policy documents. Every stage changes the same project, and you are shown exactly what changed. Pick Python or TypeScript once and the whole track follows it.

Words used in this lab

CLAUDE.md
A file in your repository holding standing project context: how to build, where things live, the conventions you follow. It loads into the session so nobody re-explains it.
Permission rules
Configuration listing which commands and paths are allowed and which are refused. In an unattended run this is the only thing between the job and a damaging command.
Hook
Your own command, run automatically at a set point such as just before a tool runs. Because it is your code it happens every time, rather than when the model remembers.
MCP server
A service offering tools and readable content to any client speaking the same protocol. Write it once and Claude Code and your own application both use it.
Skill
A written procedure in the repository, with a note saying when it applies, so the same steps run the same way for everybody.

Stages

1Write the project context down once

Stop everyone re-explaining the same things at the start of every session.

  1. Create CLAUDE.md at the project root with the facts you keep repeating.
  2. Keep it short. Everything in it loads on every session and competes with the actual task.
  3. Commit it, start a fresh session, and check the re-explaining has stopped.

2Decide what Claude Code may and may not do

Set the rules before you need them rather than after.

  1. Create the settings file with an allow list for what your work needs.
  2. Add a deny rule for the policies directory and for anything that touches your key.
  3. Try to edit a file under policies/ and confirm you are refused.
  4. Note that deny wins over allow, and that a managed policy set centrally cannot be loosened locally.

3Enforce one rule with code, not with words

Make something happen every time, without depending on anyone remembering.

  1. First try asking for it in CLAUDE.md. Work for a while and see whether it always happens.
  2. Now write the hook script and register it.
  3. The PreToolUse hook refuses writes that would put a credential into a tracked file. Exit code 2 blocks the call and sends your message back.
  4. Test it: ask Claude Code to add an API key to a config file.

What you should see

Exam lens — D3 · Claude Code. Hooks exist because always and never should not depend on the model remembering mid-session. A pre-tool hook that could not block a call would be advisory, which would defeat its purpose.
Check before you rely on this. Hook event names and the exit-code contract are configuration details that can change between releases. Check the current Claude Code documentation before relying on the exact numbers above.

4Build an MCP server for the policy documents

  2. Note the tools are narrow and purpose-built, not one that runs anything.

5Connect it, and choose how it is reached

Use one server from Claude Code, and understand when stdio is not enough.

  1. Register the server for the project so its tools appear in a session.
  2. Start a session and ask a policy question. Confirm it calls your tool rather than reading the file directly.

6Package a procedure so it runs the same for everyone

Stop a shared way of working drifting between people.

  1. Write the Skill below. The frontmatter description is what decides when it gets used, so it must say when it applies.
  2. Commit it so it is versioned and reviewed like any other file.
  3. Ask for a policy change review and confirm the Skill is applied.
  4. Have a colleague do the same and check they get the same behaviour.
Language:
.claude/skills/policy-change-review/SKILL.mdnew file
---name: policy-change-reviewdescription: >  Review a proposed change to a file under policies/. Use whenever someone  asks to check, review or approve a policy edit, or when a diff touches  policies/. Do not use for code review.--- # Reviewing a policy change 1. Show the diff for the file under `policies/`.2. Run the eval suite: any question whose expected answer depends on the   changed text will fail. Those failures are the blast list.3. For each failing question, state the old answer and the new one.4. Check the change does not contradict another policy. Cross-check any   figure that appears in more than one document.5. Confirm `verify()` still passes: the assistant must be able to quote a   real sentence for every question in the suite.6. Output a short summary: what changed, which answers change as a result,   and anything that now conflicts. Never edit the policy file yourself. The HR team owns it; you review only.

7Cut down the list of tools

Improve tool choice by offering fewer options.

  1. Count how many tools your session offers across every connected server.
  2. Run the ten questions and count wrong tool picks.
  3. Limit the project to only the servers this work needs.
  4. Run the same ten and compare.
