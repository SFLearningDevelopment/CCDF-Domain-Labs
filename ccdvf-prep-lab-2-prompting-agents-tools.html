Production-Grade Prompting, Agents and Tool Use

Turn a prompt that works once into one that works every time, then give it tools and a loop.

D6 · Prompt and Context EngineeringD8 · Tools and MCPsD1 · Agents and Workflows
0 of 7 stages done

Before you start

You will build one thing across all five labs: an internal HR Policy Assistant that answers staff questions from your company's policy documents. Each lab adds a layer to the same project, so by the end you have a single working example rather than five disconnected exercises.

Words used in this lab

Few-shot example
A worked example you include in the prompt showing the kind of answer you want. Most useful where the decision is hardest, not where it is already easy.
Prefill
Putting the first few characters of the answer into an assistant entry at the end of your messages list. Claude continues from there, so there is nowhere for a preamble to go.
Tool schema
The description and the list of parameters you give Claude for a function it can ask you to run. It is the contract between your code and the model.
tool_use and tool_result
Claude asks for a function by returning a tool_use block with an id. You run the function and send the answer back in a tool_result block carrying the same id.
Agent loop
Gather what you need, take an action, check the result, and repeat until the work is done or a limit stops you. The checking step is what makes it an agent.

Stages

1Give the prompt a clear structure

Stop the model answering from the wrong part of your prompt.

  1. Put your instructions, the policy text and the user's question in one undivided block. Ask a question whose answer appears in two places. Note what happens.
  2. Now separate the three parts with tags such as , and .
  3. Change your instruction so it refers to a section by name, for example answer using only what appears inside .
Exam lens — D6 · Prompt and Context Engineering. A question describes exactly this: three things run together and answers drawn from the wrong one. The fix is structure, not a larger model.

2Make the output shape reliable

Get an answer your code can parse every time, not most times.

  1. Ask for JSON in plain words and run it fifty times. Count how many replies your parser accepts.
  2. Now define a tool whose parameters are the shape you want, and read the structured input from the tool_use block instead.
  3. Run the same fifty and count again.
Exam lens — D6 · Prompt and Context Engineering. Asking politely for JSON works most of the time, and that is exactly what makes it risky at volume. Moving the shape into a schema turns a request into a contract.

3Aim your examples at the hard decision

Fix a confusion between two similar categories.

  1. Sort your policy questions into categories. Find two the model keeps mixing up.
  2. Add examples that sit right on the line between those two, at least one of each.
  3. Write the rule that separates them in one plain sentence and put it beside the examples.
  4. Re-run and see whether the confusion drops.
Exam lens — D6 · Prompt and Context Engineering. Adding more examples of what already works is the tempting wrong answer. Examples belong where the decision is hardest, paired with the rule that explains the difference.

4Write two tools that are hard to confuse

Make Claude pick the right function the first time.

  1. Define two related tools, for example search_policies and search_benefits.
  2. Write each description so it says what the tool covers, when to use it, and when to use the other one instead.
  3. Mark which parameters are required.
  4. Ask ten questions that sit near the line between the two and count how often the wrong one is chosen.
Exam lens — D8 · Tools and MCPs. Picking the wrong tool is a more common failure than getting the arguments wrong. The sentence that fixes it is the one saying when not to use this tool, and it is the sentence most people leave out.

5Run the tool loop by hand once

Understand the exchange before a library hides it from you.

  1. Send a question that needs a tool. Look at the response and find stop_reason set to tool_use.
  2. Find the tool_use block and read its id, name and input.
  3. Run the function yourself and send the result back in a user message, in a tool_result block carrying that same id.
  4. Break it on purpose: send back a wrong id and see what happens.
  5. Make the function throw an error, and return that as a tool result marked as an error rather than as an empty result.
Exam lens — D8 · Tools and MCPs. Questions test that results go back in the user turn and that the id is what pairs a result to its request. They also test that an empty result is worse than an error, because it reads as a successful call that found nothing.

6Close the loop and put limits on it

Let the assistant work on its own without letting it run away.

  1. Wrap your calls in a loop: send, check for a tool request, run it, send the result back, repeat.
  2. Add a check the assistant cannot argue with, such as confirming the answer quotes a real policy section.
  3. Set a limit on turns, a limit on tokens and a limit on elapsed time.
  4. Decide what happens when a limit is reached. Returning nothing is not an answer.
  5. Add a check for the same tool being called twice with the same arguments.
Exam lens — D1 · Agents and Workflows. Limits have to hold whatever the model decides, so they live in your code and not in the prompt. The part most people forget is deciding what happens when a limit is hit.

7Decide whether you needed an agent at all

Be able to justify the design you chose.

  1. Write down the steps your assistant actually takes for a typical question.
  2. Ask whether those steps are the same every time. If they are, write the fixed version and compare cost and speed against the loop.
  3. Write one paragraph saying which you would ship and why.
Exam lens — D1 · Agents and Workflows. When the steps are known in advance and never vary, a fixed sequence is cheaper, quicker and easier to test. Reaching for an agent by default is the most common overbuild.

Finish this lab

When every stage above is ticked, mark the lab complete. Then try Intermediate Set 2, especially the prompting, tool and agent questions and see which questions you can now answer from something you have actually built.
