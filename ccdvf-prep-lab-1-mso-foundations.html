Before you start

You will build one thing across all five labs: an internal HR Policy Assistant that answers staff questions from your company's policy documents. Each lab adds a layer to the same project, so by the end you have a single working example rather than five disconnected exercises.

Words used in this lab

Context window
One shared budget for everything you send plus the reply Claude writes. Your system prompt, the conversation so far, your tool definitions and the answer all come out of the same allowance.
max_tokens
The most tokens the reply is allowed to use. It is a ceiling, not a target. Setting it high does not make answers longer, but it does reserve room inside the context window.
stop_reason
A field on the response telling you why Claude stopped writing. Check this field rather than reading the text to work out what happened.
Prompt caching
Paying less for a large piece of text you send unchanged on many requests. The saving only applies if that text sits at the very start of the request and does not change.
Model tier
The family of models from fastest and cheapest up to most capable. Picking a tier is a trade between cost, speed and quality.

Stages

1Make one working request

Send a single question to the Messages API and get an answer back.

  1. Write the smallest request that works: a model name, a messages list holding one user message, and max_tokens.
  2. Put your instructions in the top-level system parameter, not in the messages list. The messages list only accepts user and assistant entries.
  3. Send it and read the answer.
Exam lens — D2 · Applications and Integration. Exam questions test whether you know that the system prompt is its own parameter and that max_tokens is required. Both are easy marks if you have typed the request yourself.

2Read the whole response, not just the text

Learn what the response tells you besides the answer itself.

  1. Print the full response object rather than only the text.
  2. Find stop_reason and note its value. Ask for a very short max_tokens and send the same request again, then look at how stop_reason changed.
  3. Find the usage figures and write down how many tokens went in and how many came out.
Exam lens — D2 · Applications and Integration. You will be asked what a given stop_reason means and how to branch on it. Seeing the value change when you shorten max_tokens makes the difference stick.

3Compare three tiers on the same work

Choose a model from measurements instead of assumption.

  1. Write ten real policy questions with the answer you would accept for each.
  2. Run all ten against a fast low-cost model, then against a mid model, then against the most capable one. Keep the prompt identical.
  3. For each run record three things: how many answers were acceptable, how long it took, and what it cost.
Exam lens — D5 · Model Selection and Optimisation. The exam repeatedly asks which tier to try first for a narrow, high-volume task. The answer is the cheapest one that clears your bar, with a route to escalate the cases it cannot handle.
Check before you rely on this. Model names, prices and speeds change. Check current model documentation for the tiers available to you rather than relying on a name you have seen before.

4Find out where your tokens actually go

See whether your spending is on what you send or on what comes back.

  1. Take your best run from stage 3 and add the policy document to the request.
  2. Compare input tokens against output tokens.
  3. Multiply out what that would cost across a realistic daily volume.
Exam lens — D5 · Model Selection and Optimisation. Several questions hinge on noticing that a bill is dominated by input. If it is, shortening the answer does nothing and the fix lies in what you send.

5Turn on caching and prove it worked

Cut the cost of re-sending the same large document.

  1. Reorder your request so the unchanging content comes first and the user's question comes last.
  2. Mark the end of the unchanging part so it can be cached.
  3. Send the same request twice and compare the reported cache figures between the two runs.
  4. Now deliberately move the question to the front and send it twice more. Watch the caching stop working.
Exam lens — D5 · Model Selection and Optimisation. A common question describes caching that never takes effect because a changing piece of text sits at the start of the request. Breaking it on purpose is the fastest way to understand why.

6Run the same work as a batch

See what you gain when nobody is waiting for the answer.

  1. Take fifty policy questions that no user is waiting on.
  2. Submit them as a batch rather than as fifty live requests.
  3. Compare the price per question against your live runs, and note how long the batch took.
Exam lens — D5 · Model Selection and Optimisation. When a question says high volume, overnight, and cost is the binding constraint, batch processing is the answer. Trading time you do not need for a lower price is the whole idea.

7Write your model decision down

Record the choice so it can be revisited when something changes.

  1. Write a short note: which tier you chose, the numbers that led you there, and what result would make you change your mind.
  2. Note where the model name is set in your code. If it is written into the source, move it into configuration.
  3. Write down how you would roll back if a newer model made things worse.
Exam lens — D5 · Model Selection and Optimisation. Keeping the model name in configuration is what lets you pin a version, move forward and roll back without shipping code. This shows up in both model selection and configuration questions.

Finish this lab

When every stage above is ticked, mark the lab complete. Then try Basic Set 1 and the model selection questions in Intermediate Set 2 and see which questions you can now answer from something you have actually built.
