Accelerators and IP Contribution

Take what you built, make it faster and cheaper, and package it so other people can use it.

D2 · Applications and IntegrationD5 · Model Selection and OptimisationD3 · Claude Code
0 of 7 stages done

Before you start

You will build one thing across all five labs: an internal HR Policy Assistant that answers staff questions from your company's policy documents. Each lab adds a layer to the same project, so by the end you have a single working example rather than five disconnected exercises.

Words used in this lab

Accelerator
Something you build once and reuse, so the next project starts further along than the last one did.
Versioned prompt
A prompt kept in the repository like code, reviewed when it changes, with a record of which version each deployment ran.
Compaction
Summarising older parts of a conversation into a short running note and keeping only recent turns word for word, so cost and quality stop degrading as it gets longer.
Runbook
A short document telling somebody else how to run, check and fix the thing you built, without asking you.
Model pinning
Naming an exact model version in configuration so an upgrade is a decision you make and can undo, rather than something that happens to you.

Stages

1Find what you would rather not do again

Spot the reusable parts of the last four labs.

  1. List everything you built across labs 1 to 4.
  2. Mark each item as specific to this project or useful on the next one too.
  3. Pick the three most reusable and write one line on what each saves.
Exam lens — D2 · Applications and Integration. Knowing which parts of a working system are reusable is the difference between finishing a project and building something your team keeps.

2Turn your best prompt into a proper artifact

Stop the prompt being something that lives in one person's file.

  1. Move your best prompt into the repository as a file that gets reviewed when it changes.
  2. Pick which version to use from configuration, per environment.
  3. Record which prompt version each deployment is running, so any answer can be traced back.
  4. Change it, review the change, and check you can tell afterwards which version produced which answer.
Exam lens — D2 · Applications and Integration. Editing prompts live in a database is the tempting wrong answer. It is fast, and that is the problem: no review and no history is how versions drift apart between environments.

3Apply the cost and speed levers together

Make the assistant noticeably cheaper and quicker.

  1. Put your unchanging content at the start of the request and cache it.
  2. Route the easy majority of questions to a fast cheap model, and send only the ones it cannot handle confidently to a stronger one.
  3. Send anything nobody is waiting on as a batch.
  4. Shorten what your tools return so only the fields the next decision needs come back.
  5. Measure cost and speed before and after.
Exam lens — D5 · Model Selection and Optimisation. Shortening what a tool returns matters more than it looks. A long result is charged again on every later turn of the same task, so trimming it once saves repeatedly.

4Stop the conversation getting worse as it gets longer

Keep quality steady in a long session.

  1. Hold a forty-turn conversation and watch cost, speed and answer quality as it goes.
  2. Summarise older turns into a short running note, keep the recent ones word for word, and fetch older detail only when it is needed.
  3. Run the same forty turns again and compare.
  4. Check the assistant still remembers what the user expects it to remember.
Exam lens — D6 · Prompt and Context Engineering. Starting a fresh conversation fixes the cost but throws away what the user expects you to know, trading a speed problem for a product one.

5Package it so somebody else can use it

Make it reusable without you in the room.

  1. Take your most reusable piece and package it: a Skill, a template repository, or a small library.
  2. Include a short note saying when it applies and when it does not.
  3. Version it.
  4. Give it to a colleague with no explanation and watch where they get stuck. Fix that, not what you assumed would confuse them.
Exam lens — D3 · Claude Code. Packaging is what turns a habit one person maintains into something a team owns. The note saying when it applies is what lets it be used at the right moment.

6Write the runbook

Let somebody else run and repair it.

  1. Write down how to run it, how to tell it is healthy, and the three most likely failures with what to do about each.
  2. Record which model version is pinned and how to move to a new one safely: test against the eval set first, then promote, with a way back.
  3. Note where the recorded runs live and how to find one.
  4. Ask somebody to follow it while you stay silent.
Exam lens — D2 · Applications and Integration. Pinning the model version is what makes an upgrade a decision rather than an event, and the eval set is what turns seems better into evidence.

7Check yourself against the exam domains

Find your remaining gaps before the exam does.

  1. Go through the eight exam domains and write one sentence on what you built for each.
  2. Any domain where you cannot write that sentence is a gap. Go back to the lab that covers it.
  3. Take a prep set and note which domain each wrong answer belongs to.
  4. Return to the matching stage in these labs rather than only rereading the explanation.
Exam lens — All eight domains. The exam weights domains unevenly. Applications and Integration is by far the largest, and Model Selection and Optimisation is second, so gaps there cost the most marks.

Finish this lab

When every stage above is ticked, mark the lab complete. Then try Advanced Set 3, then any domain where you scored below seventy per cent and see which questions you can now answer from something you have actually built.
